# Public groups

Anagram public groups use ordinary relays. They are public, with client-side moderation; blocking cannot stop someone reading or publishing through another client.

- Room: creator-signed `kind:34550`, stable `d`, `name`, `description`, optional `image`, 1–8 `relay` tags and `["anagram-room", "1"]`.
- Policy: repeated `trusted` and `blocked` pubkey tags in the room definition. Owner is implicitly trusted; blocking wins. These are Anagram extensions, not NIP-51 follow sets or NIP-72 approval moderation. NIP-72 currently recommends NIP-29 instead; this client deliberately uses the public definition format on ordinary relays.
- Messages: signed NIP-C7 `kind:9`, exactly one `a` tag containing `34550:<owner>:<d>`. Trusted attachments use NIP-92 `imeta` tags. Sharing uses NIP-19 `naddr`; relay hints do not change room identity.
- Message actions: NIP-C7 `q` tags carry replies, NIP-25 `kind:7` events carry reactions, and NIP-09 `kind:5` events request deletion of specific event IDs. Deletion requests use `e` tags, never the room's `a` coordinate (which would request deletion of its definition). Anagram adds an `h` room hint to reactions/deletions for discovery; standard events without that hint are also read through bounded subscriptions to the visible event IDs.
- Edits reuse the private-group delete-and-replace flow described in NIP-17: publish a deletion request for the previous version, then a `kind:9` replacement with the same timestamp. The existing Anagram `e` tag marked `edit` links the previous version; a further ordinary `e` reference preserves the original ID for bounded lookup after repeated edits. Only the same author, room and timestamp can form an edit chain. The edit-link marker is an Anagram extension, not part of NIP-C7 or NIP-17.
- Forwarding uses the shared private-chat forward picker and copies the visible content/attachments into a new message in the selected DM, private group or public group. It preserves the private-chat behavior (no original sender attribution or reply metadata); it is not a NIP-18 repost. Public destinations enforce their own media/trust policy.
- Transfer: the new owner's fresh room signs a `predecessor` coordinate. The old owner signs a `successor` coordinate plus an optional relay hint. Both signatures and the reciprocal binding are required. Accepted transfers are pinned locally; cycles and chains exceeding eight rooms are rejected. The successor's policy controls rendering, including explicitly selected predecessor history. Old events retain their original addresses and signatures.

Untrusted messages use escaped text with web links replaced by `[link removed]`, without rich parsing or remote media. This applies to cached messages too. Blocking and trust changes also affect cached messages. Trusted posts use the shared chat message renderer, including lazy images, video controls and the image viewer. Media URLs must pass the public HTTPS URL filter; browser media elements follow storage-host redirects just as in private chats. Untrusted posts pass only literal, redacted text to the shared message body, with no links, attachments or remote avatars. Link previews keep their bounded, credential-free, redirect-rejecting fetch policy. Browser DNS/network policy still applies; no server-side media or preview proxy is added.

Room subscriptions run while the room is open. Messages stay in account-scoped IndexedDB, with a 200-message display window, a 2,000-message per-room disk cache and a separate bounded 8,000-event action cache; earlier history is paged from relays. Background public notifications and cross-device subscriptions are not implemented. Leaving removes the local subscription; opening the link joins again.

Thread search reuses the DM/private-group search bar, result navigation and message highlighting. It searches the selected room's downloaded cache (including selected predecessor history), with up to 100 newest matches. Load earlier messages to include more history. Search applies the current owner's blocklist and link redaction, and opens a bounded window around a match without fetching the full history. Results and pending jumps are discarded when the account, room or signed policy changes.

Relay bars reuse the normal message details dialog and record actual receipts and publish acknowledgements locally; failed sends can retry the original signed event. Rendering stats adds no relay queries.

Saved rooms and a bounded message window display immediately while hydration runs in the background. A signed policy from a relay that completed a real EOSE read can establish the room without waiting for an unavailable replica; older policies never replace a newer cached version. Live updates continue to apply newer owner-signed policy. Public groups read and publish through the group's preferred relays and the configured app relays. Owners choose preferred relays during creation or in the Relays tab. Owner edits use the same completed-read check; one relay acknowledging publication confirms any update or message. Failed or stalled replicas do not block success on a working relay. Relay changes are also published to the previous relays so old links can discover the change, but earlier messages are not copied to replacements. Offline clients can display previously verified policy but cannot post. A fresh client can still miss a handover or blocklist update if relays withhold it: signatures prove authorship, not global freshness. Concurrent owner edits use ordinary NIP-01 replacement ordering, with a refresh-before-save check.

## Shared interface

DMs, private groups and public groups share the thread header, timeline, message rows, date dividers, sender grouping, text/bubble layout, composer, emoji and mention controls, message menus, event details and upload confirmation. Reply previews, edit/reply composer context, forwarding destinations and reaction details also use shared components. Public moderation supplies sanitized text/media and restricts writes in read-only history or for blocked users; it does not define another chat layout. Group settings reuse profile fields, relay editing, member rows, tabs and modal framing. Protocol and storage operations remain in their respective runtimes.

Chat-list search matches joined group names, descriptions and identifiers and discovers signed public groups on the account’s read relays. It uses NIP-50 plus a separate bounded read of up to 100 recent room definitions per relay. The ordinary read still works when a relay rejects search filters or does not index group-name tags. Profile search uses the same independent fallback, limited to 100 recent profiles per relay. Discovery returns at most 20 matches, excludes joined duplicates and blocked creators, and does not join a group until a result is opened. This is relay-scoped discovery, not an exhaustive directory.
